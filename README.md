## Design

SQLite app tables + supplier CSVs → DuckDB `raw` → dbt staging → silver / quality → gold → Iceberg.

| Model | Layer | Grain (one row per ...) | Materialization |
|---|---|---|---|
| `stg_supplier_prices` | staging | supplier price row | view |
| `stg_orders` | staging | eligible delivered order | view |
| `product_cost_history` | silver | SKU and cost version | table |
| `weekly_margin` | gold | ISO week, city and category | table |
| `price_quarantine` | quality | rejected supplier price row | table |

The supplier files are loaded as text first so values such as decimal commas and Arabic-Indic digits are not lost during ingestion. In staging, SKUs are trimmed and costs are normalized before conversion to numbers.

For the SCD2 history, I first keep only valid supplier rows. If the same SKU and `valid_from` appear more than once, the filename that sorts last wins, which makes the correction file replace the original quote. A new history version is created only when the cost changes. Missing weeks do not create a row, so the previous cost stays valid until a later changed cost appears.

Each order line is matched to the cost version where `valid_from <= order_date < valid_to`. The final version has a null `valid_to`. A line with no cost still contributes to line count and revenue, but not to the cost or margin columns.

## Data problems I found

| Problem | Where | Rows affected on the course dataset | What I did |
|---|---|---:|---|
| Invalid supplier costs | supplier CSVs | 4 | quarantined as `invalid_cost` |
| Unknown SKUs | supplier CSVs | 3 | quarantined as `unknown_sku` |
| `unit_cost` renamed to `cost_sar` | week 39 file | 160 | loaded files with `union_by_name` and used either cost column |
| Decimal commas | week 38 file | 126 | replaced comma with decimal point before casting |
| Arabic-Indic digits / Arabic decimal mark | week 38 file | 34 | translated digits and normalized the decimal mark |
| Trailing spaces in product SKUs | products | 2 | trimmed SKUs on both sides of matching |

## Tests

The dbt project includes more than the required six tests. It checks required fields, unique order IDs, accepted quarantine reasons, duplicate SCD2 versions, exactly one current version per SKU, repeated unchanged costs, valid SCD2 intervals, and weekly margin arithmetic.

## Re-runs and the correction

A second run with the same input does not change the Iceberg tables because the new rows are compared with the current table before publishing.

On the provided course dataset, the total gross margin is SAR 801,016.88 before the week 39 correction and SAR 803,515.80 after it, a change of SAR 2,498.92. The publish step updates the existing Iceberg table instead of dropping it, so the pre-correction snapshot remains available for time travel.

Snapshot IDs are generated by Iceberg at runtime, so I record the IDs from the warehouse used for submission when doing the final local run.

## What I'd do next

With much more data, rebuilding and comparing whole tables would become expensive. I would make the transformations incremental and only recompute the weeks affected by new supplier files or corrections. If supplier files arrived daily, I would also track which files had already been ingested and add stronger file-level validation before they enter the raw layer.
